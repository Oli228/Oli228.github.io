  • 기술/모델 전략:1~5단
    • 시설 고장/파손 예측 AI (2단: 전통ML 자체구축)
      • 전통 ML 모델/알고리즘을 상용도구로 도입하거나 자체구축할지
      • AutoML(Automated Machine Learning)으로 자체모델개발 검토
        1. 모델알고리즘 선택(logistics, randomforest 등),
        2. 데이터 요구사항(학습/검증 데이터범위, 라벨링 기준, 데이터 품질 기준 정의)
        3. 피처 엔지니어링(피처 설계 전략, 변수선택 기준 명시)
        4. 학습/검증 방식(훈련/테스트 분리, 상호검증 전략)
        5. 성능/성공 기준(KPI 기반 성능 목표- 정확도, 재현율, 설명력 등) 명확화
        6. 해석가능성(모델 설명 가능성(xai) 요구사항)
        7. 운영/재학습 전략(재학습 주기, 드리프트 감지 등)
        8. 인프라 요구사항(학습, 서빙 인프라 직접 설계)
        9. 확장/고도화(향후 딥러닝 적용 가능한 구조로 요구)
    • 시설 분류 AI (3단: 딥러닝)
      • 고성능 모델 + 대규모 데이터 + GPU 인프라 + 운영전략을 함께 설계해야 하는 단계
      • 데이터 규모가 충분히 확보되어 있는지 등 딥러닝은 고려해야 할 내용들이 복잡해짐
        • 모델 전략, 인프라, 데이터 전략, 성능 기준, 설명가능성, 재학습/운영, 보안/IP, 테스트/검증, 책임/거버넌스

    1. 기능 요구사항: 기능 나열이 아니라 ‘모델이 어떤 판단을 어떻게 수행해야 하는지’, 실패/오류 시 행동규칙 포함 필수
      1. AI 처리 로직(분류)
      2. 예외처리(불확실성 응답정책)
      3. 응답정책(금지 응답, 휴먼 에스컬레이션)
    2. 성능 요구사항: 단발성 아니라 운영 중 성능 유지 기준, 측정방식과 평가데이터 기준값 함께 명시
      1. 정확도, 환각률, 응답품질, 응답시간(SLA), 처리량, 동시 사용자 수
    3. 시스템 구성 요구사항: 단순 장비 스펙이 아니라 운영 가능한 구조여야 하며 비용, 확장, 성능 균형 구조 명시
      1. GPU, CPU 자원, API 기반 모델, 하이브리드 구조
      2. 모델 서빙 구조, MLOps 인프라
      3. 확장전략
    4. 인터페이스 요구사항: UI/화면이 아니라 ‘모델-툴-시스템 간 흐름’에 대해 명시
      1. API 연계 방식
    5. 데이터 요구사항: 단순 저장이 아닌
      1. 학습데이터 범위, 출처, 품질 기준
    6. 테스트 요구사항: 기능 테스트 + Ai특화 평가(환각, 편향, 안전) 포함
      1. 모델 성능 평가 시나리오
      2. 운영 전/후 품질 검증 체계
    7. 보안 요구사항: 전통 보안 + 모델 오남용/프롬프트 공격 리스크 포함
    8. 품질 요구사항: 모델 출력 안정성 관점으로 확장, 변경 이력 및 버전 관리 명시
      1. 모델 버전 관리
      2. 응답 일관성 관리
      3. 결과 재현성 확보
    9. 제약사항: ‘요구’가 아니라 AI 적용 시
      1. 용역계약일반조건에 따른 책임 한계
      2. 모델/IP 귀속 구조의 제약
      3. 재학습 권한, 비용 범위의 계약상 제한
    10. 프로젝트 관리 요구: 단계적 고도화, 실험허용 구조, 실패/개선 사이클 명시
      1. PoC-> 단계적 확산전략
      2. 반복 개선 체계
      3. 모델 성능 개선 로드맵
    11. 프로젝트 지원 요구: 기술 지원이 아니라 AI 운영 역량 내재화해야 함
      1. 데이터, 운영 협업 구조
      2. 내부담당자 역량 이전
      3. 사용자 교육(모델 사용 주의 포함)
    12. 유지관리 요구: 유지보수가 아니라 모델 생애주기 관리
      1. MLOps 운영 체계
      2. Drift 대응 및 재학습 프로세스
      3. 성능 저하 대응 정책
    13. 유지관리 인력 요구: 인원 수가 아니라 역할, 책임, 권한 구조 명확화
      1. 모델 운영 책임자
      2. 데이터, AI 운영 인력 역량 요건
      3. 휴먼인더룹 책임 구조 추가
    14. 그 외 13개 요구사항에 매핑되지만 부족하거나 깔끔하게 매핑되지 않는 영역
      1. 모델/프롬프트/지식구조전략: 별도 설계 원칙으로 명시 권장
      2. 휴먼인더룹: 기타 운영, 통제조건에 별도 명시
      3. 드리프트 관리, 재학습, 모델 생명주기: 유지관리 요구사항에 포함하되 AI모델 생명주기 관리라는 하위항목을 명시적으로 추가하는 것이 좋음
      4. AI거버넌스/책임구조/윤리체계: 기타 운영, 통제조건에 별도 명시
      5. 비용구조/토큰,GPU,API소비관리: AI사용량 기반 비용통제조건 별도 명시
      6. 툴 연계/에이전트 실행통제: 인터페이스 요구사항+ 프롬프트 관리 요구사항 => 자동실행/에이전트 통제정책 별도 서술 권장
      7. 모델선택, 벤더전략, IP 전략

10강. 계약조건 설계 이해

1. 기존 IT기업 계약 이해

  • 계약은 상호대등한 입장에서 당사자의 합의에 따라 체결
  • 계약문서: 계약서, 유의서, 용역계약일반조건, 용역계약특수조건, 과업내용서 및 산출내역서
  • 용역계약특수조건으로 적정한 이행을 요구
  • 용역(Service)계약일반조건
    • 관련용어
      • (추가과업) 용역 목표달성과 연관되어 요구하는 내용
      • (특수과업) 업무와 무관하지만 요구하는 내용
    • 제4장 소프트웨어용역 계약조건은 AI 사업관리에 바로 적용하기 어려운 구조
      • 하자보수가 결함이 아닌 성능 유지로 전환해야 함(성능 저하 시 재학습, 보정 책임)
      • 개발과 운영이 분리된 기존 SW사업에서 장기계속계약(개발+운영)으로 전환해야 함
      • 성능이 동적일 때에는 성능 모니터링 및 리포팅 의무가 중요함
      • 성능 하락 시 개선 SLA 정의해야 함
      • 데이터 재학습 활용 조건, 프롬프트 영업비밀 보호 등 IP 관련 쟁점 다뤄야 함
      • AI 판단 오류와 책임 소지를 다루기 위해 휴먼인더룹 의무화, 자동화 적용범위를 명시
      • 윤리, 차별, 설명가능성 계약 관련 고려가 전혀되어 있지 않으므로 추가반영해야 함

  • AI특화 계약특수조건(안)
    - 제안요청서 공개 시 특수조건 함께 첨부, 기술 협상 때 수정하고 관인

1강. AI 사업의 본질적 차이 및 실패원인

  • AI사업 완료의 기준은 MLOps(지속적개선)의 시작으로 정의
  • AI사업은 ISP가 아닌 BPR이 먼저 선행되어야 함
  • AI사업은 전통IT 사업과는 다른 고유한 사업특성이 있음
    • (전통) ISP-> 구축-> 운영의 선형적 접근 (정해진 길 가기)
    • (반복진화형) 평가-> 준비-> 선택-> 구현-> 통합 (길 찾아가기)

2강. 실패를 막는 5단계 반복/진화형 프로세스

  • 구축 중심 개발이 아닌, 반복/진화형 관리 프로세스
    => 사업완료의 기준을 MLOps의 시작으로 재정의해야 하는 이유
  • 평가단계: AI사업 타당성 검토 및 프로젝트 기반 마련
    • 비즈니스 가치가 명확히 정의?
    • AI가 이 문제 해결의 올바른 기술인가?
    • 프로젝트를 다음 단계로 진행할 준비가 되었는가?
  • 준비단계: 프로젝트 실행에 앞서 조직 데이터, 기술, 인력, 프로세스 등의 준비 상태 점검, 강화
    • 프로젝트 자원 충분이 확보?
    • 현실적이고 실행가능?
    • 조직은 AI솔루션을 선택할 준비가 되었는가?
  • 선택단계: 다양한 AI 솔루션을 평가, 기술검증으로 최적의 솔루션 최종선택
    • PoC 결과가 프로젝트의 성공가능성을 입증하는가?
    • 선정된 솔루션이 기술적, 재무적, 법적 요구사항을 모두 만족?
    • 이제 본격적인 구현 단계로 넘어갈 준비가 되었는가?
  • 구현단계: 선택된 솔루션을 실제 운영환경에서 파일럿 형태로 구축하고 테스트하는 단계
    • 파일럿 결과가 사전에 정의된 성공 기준을 충족했는가?
    • AI 솔루션이 전체 조직으로 확산될 준비가 되었는가?
    • 통합 단계로 진행하기 위한 리더십의 최종 승인이 이뤄졌는가?
  • 통합단계: 검증된 AI솔루션을 조직의 전체 업무 프로세스와 시스템에 완전히 통합하고 지속적으로 운영 및 개선하는 마지막 단계
    • MLOps 파이프라인 구축

3강. 기술 도입이 아닌 문제/가치 중심의 기획 접근법

  • 피해야 할 AI활용사례: 개인의 권리, 안전, 기본권, 환경에 중대한 영향을 미치는 분야
    • 도입 전 반드시 위험평가 수행(편향, 공정성, 투명성, 개인정보, 책임성 등)
      • 일부 영역은 AI 보조적 활용만 허용, 자동화는 금지
  • 핵심문제정의 및 가치 정렬
    • 핵심문제:
      • (안전/위험) 파손, 고장난 시설로 인한 이용객들의 안전 위협 및 민원 제기 높음
      • (고비용/예측) 사후중심의 시설보수로 보수비용 증가 및 예산예에 어려움 있음
    • 핵심가치:
      • 시설고장 예측으로 연간 보수를 위한 비용 절감 및 예산계획 수립
      • 시설고장 관련 민원량 감소
    • 목표정렬:
      • 사후 보수에서 사전 예방으로 전환하여 시설관리정책 관련 보틀넥 해소
      • 선제적 대국민 서비스 제공으로 대국민 만족도 제고
  • 성과(KPI) 기준 수립
    • (가치KPI)
      • 시설 관련 이용객 민원량 전년대비 20% 감소
      • 시설 관련 사후보수 비용 전년대비 30% 감소, 사전예방 비용 30% 증가
    • (기술KPI)
      • (분류모델) 시설 유형 자동분류 모델 정확도 95% 이상
      • (객체 탐지 모델) 이미지 내 시설 탐지 재현율(Recall) 95% 이상
      • (회귀/예측 모델) 설비 ‘고장/파손 시점’예측모델의 평균 제곱근 오차(RMSE) 3일 내

4강. 주요 AI 기술별 특성 및 문제 - 기술 적합성

  • AI는 생성형AI(LLM)가 아님
  • 시설고장/파손 예측은 정답맞히기가 목표로 분류 및 예측하는 머신러닝 적용이 적절함
  • 문제-기술 적합성 검토
    • 비AI대안 검토: 없음
  • 문제정의, 가치설계 결과 명료화
    • 해결하려는 핵심문제: 시설 고장/파손 예측이 어려워 사전보수가 불가함
    • 문제유형: 분류+예측
    • 기대가치: 안전사고 및 민원량 감소, 사후보수 비용 감소
    • 성공기준API: 시설관련 이용객 민원량 전년대비 20% 감소
    • 활용주체: 본사 공원시설부, 공원사무소 시설과 직원
    • 자동화 허용 범위: 의사결정 보조
  • 기술 선택 전 필수 조건 정리
    • 문제 중요도: 중간 단순 빈도나 공적 영향 중심
    • 정책권리 영향: 있음 AI모델이 고장/파손 예측되지 않은 경우, 안전문제 발생 시 심각한 민원으로 야기될 가능성 높음
    • 실시간성 요구: 비실시간 월별 리포트로 충분할 것으로 보임
    • 설명 가능성 요구: 높음 결과에 대한 이의제기, 감사, 책임 설명 가능성 요구 높기 때문에 복잡하고 설명불가한 모델(예. LLM) 사용하지 않는 것을 권고
  • 기술 선택을 위한 최소 정보 점검=>“데이터 있음+품질낮음으로 데이터 보완” 선행해야 함
    • 데이터 존재 여부: 있음
    • 데이터 형태: 정형(구조화)+비정형(비구조화) 비정형 많으면 고급모델 필요, 범위축소
    • 데이터 품질: 낮음 결측, 오류, 표준화 수준을 종합 고려한 대략적 품질 판단
    • 데이터 변화 가능성: 높음 변화 가능성이 높을수록 모델 재학습 및 운영 부담 증가
    • !! 판정라벨: 데이터있음+품질낮음+변화 높음=> B.데이터보완 필요,C.운영설계 필수
    • !!! 기술전략: 데이터품질이 낮아 고급모델 즉시 적용보다 데이터 정제, 표준화과제 선행 필요하며 기술 수준을 보수적으로 설정하는 전략이 합리적임
    • !!!! STEP1,2와의 연결해석: 설명가능성 요구가 높고 정책, 권리 영향이 존재하므로 불투명한 고급모델보다는 설명가능한 전통ML 중심 접근이 우선 고려됨
