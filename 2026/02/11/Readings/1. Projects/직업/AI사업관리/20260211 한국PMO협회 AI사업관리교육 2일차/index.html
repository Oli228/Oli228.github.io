  • 기술/모델 전략:1~5단
    • 시설 고장/파손 예측 AI (2단: 전통ML 자체구축)
      • 전통 ML 모델/알고리즘을 상용도구로 도입하거나 자체구축할지
      • AutoML(Automated Machine Learning)으로 자체모델개발 검토
        1. 모델알고리즘 선택(logistics, randomforest 등),
        2. 데이터 요구사항(학습/검증 데이터범위, 라벨링 기준, 데이터 품질 기준 정의)
        3. 피처 엔지니어링(피처 설계 전략, 변수선택 기준 명시)
        4. 학습/검증 방식(훈련/테스트 분리, 상호검증 전략)
        5. 성능/성공 기준(KPI 기반 성능 목표- 정확도, 재현율, 설명력 등) 명확화
        6. 해석가능성(모델 설명 가능성(xai) 요구사항)
        7. 운영/재학습 전략(재학습 주기, 드리프트 감지 등)
        8. 인프라 요구사항(학습, 서빙 인프라 직접 설계)
        9. 확장/고도화(향후 딥러닝 적용 가능한 구조로 요구)
    • 시설 분류 AI (3단: 딥러닝)
      • 고성능 모델 + 대규모 데이터 + GPU 인프라 + 운영전략을 함께 설계해야 하는 단계
      • 데이터 규모가 충분히 확보되어 있는지 등 딥러닝은 고려해야 할 내용들이 복잡해짐
        • 모델 전략, 인프라, 데이터 전략, 성능 기준, 설명가능성, 재학습/운영, 보안/IP, 테스트/검증, 책임/거버넌스

    1. 기능 요구사항: 기능 나열이 아니라 ‘모델이 어떤 판단을 어떻게 수행해야 하는지’, 실패/오류 시 행동규칙 포함 필수
      1. AI 처리 로직(분류)
      2. 예외처리(불확실성 응답정책)
      3. 응답정책(금지 응답, 휴먼 에스컬레이션)
    2. 성능 요구사항: 단발성 아니라 운영 중 성능 유지 기준, 측정방식과 평가데이터 기준값 함께 명시
      1. 정확도, 환각률, 응답품질, 응답시간(SLA), 처리량, 동시 사용자 수
    3. 시스템 구성 요구사항: 단순 장비 스펙이 아니라 운영 가능한 구조여야 하며 비용, 확장, 성능 균형 구조 명시
      1. GPU, CPU 자원, API 기반 모델, 하이브리드 구조
      2. 모델 서빙 구조, MLOps 인프라
      3. 확장전략
    4. 인터페이스 요구사항: UI/화면이 아니라 ‘모델-툴-시스템 간 흐름’에 대해 명시
      1. API 연계 방식
    5. 데이터 요구사항: 단순 저장이 아닌
      1. 학습데이터 범위, 출처, 품질 기준
    6. 테스트 요구사항: 기능 테스트 + Ai특화 평가(환각, 편향, 안전) 포함
      1. 모델 성능 평가 시나리오
      2. 운영 전/후 품질 검증 체계
    7. 보안 요구사항: 전통 보안 + 모델 오남용/프롬프트 공격 리스크 포함
    8. 품질 요구사항: 모델 출력 안정성 관점으로 확장, 변경 이력 및 버전 관리 명시
      1. 모델 버전 관리
      2. 응답 일관성 관리
      3. 결과 재현성 확보
    9. 제약사항: ‘요구’가 아니라 AI 적용 시
      1. 용역계약일반조건에 따른 책임 한계
      2. 모델/IP 귀속 구조의 제약
      3. 재학습 권한, 비용 범위의 계약상 제한
    10. 프로젝트 관리 요구: 단계적 고도화, 실험허용 구조, 실패/개선 사이클 명시
      1. PoC-> 단계적 확산전략
      2. 반복 개선 체계
      3. 모델 성능 개선 로드맵
    11. 프로젝트 지원 요구: 기술 지원이 아니라 AI 운영 역량 내재화해야 함
      1. 데이터, 운영 협업 구조
      2. 내부담당자 역량 이전
      3. 사용자 교육(모델 사용 주의 포함)
    12. 유지관리 요구: 유지보수가 아니라 모델 생애주기 관리
      1. MLOps 운영 체계
      2. Drift 대응 및 재학습 프로세스
      3. 성능 저하 대응 정책
    13. 유지관리 인력 요구: 인원 수가 아니라 역할, 책임, 권한 구조 명확화
      1. 모델 운영 책임자
      2. 데이터, AI 운영 인력 역량 요건
      3. 휴먼인더룹 책임 구조 추가
    14. 그 외 13개 요구사항에 매핑되지만 부족하거나 깔끔하게 매핑되지 않는 영역
      1. 모델/프롬프트/지식구조전략: 별도 설계 원칙으로 명시 권장
      2. 휴먼인더룹: 기타 운영, 통제조건에 별도 명시
      3. 드리프트 관리, 재학습, 모델 생명주기: 유지관리 요구사항에 포함하되 AI모델 생명주기 관리라는 하위항목을 명시적으로 추가하는 것이 좋음
      4. AI거버넌스/책임구조/윤리체계: 기타 운영, 통제조건에 별도 명시
      5. 비용구조/토큰,GPU,API소비관리: AI사용량 기반 비용통제조건 별도 명시
      6. 툴 연계/에이전트 실행통제: 인터페이스 요구사항+ 프롬프트 관리 요구사항 => 자동실행/에이전트 통제정책 별도 서술 권장
      7. 모델선택, 벤더전략, IP 전략

10강. 계약조건 설계 이해

1. 기존 IT기업 계약 이해

  • 계약은 상호대등한 입장에서 당사자의 합의에 따라 체결
  • 계약문서: 계약서, 유의서, 용역계약일반조건, 용역계약특수조건, 과업내용서 및 산출내역서
  • 용역계약특수조건으로 적정한 이행을 요구
  • 용역(Service)계약일반조건
    • 관련용어
      • (추가과업) 용역 목표달성과 연관되어 요구하는 내용
      • (특수과업) 업무와 무관하지만 요구하는 내용
    • 제4장 소프트웨어용역 계약조건은 AI 사업관리에 바로 적용하기 어려운 구조
      • 하자보수가 결함이 아닌 성능 유지로 전환해야 함(성능 저하 시 재학습, 보정 책임)
      • 개발과 운영이 분리된 기존 SW사업에서 장기계속계약(개발+운영)으로 전환해야 함
      • 성능이 동적일 때에는 성능 모니터링 및 리포팅 의무가 중요함
      • 성능 하락 시 개선 SLA 정의해야 함
      • 데이터 재학습 활용 조건, 프롬프트 영업비밀 보호 등 IP 관련 쟁점 다뤄야 함
      • AI 판단 오류와 책임 소지를 다루기 위해 휴먼인더룹 의무화, 자동화 적용범위를 명시
      • 윤리, 차별, 설명가능성 계약 관련 고려가 전혀되어 있지 않으므로 추가반영해야 함

  • AI특화 계약특수조건(안)
    - 제안요청서 공개 시 특수조건 함께 첨부, 기술 협상 때 수정하고 관인
